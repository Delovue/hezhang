### 首版边界

- 采用 Web 应用，优先保证电脑浏览器体验；演示电脑本地运行完整前后端和数据库。
- 只使用人民币，以整数“分”保存金额；每笔费用只有一个付款人，可以选择部分成员分摊。
- 角色只有活动创建者和普通成员，无平台管理员后台。
- 提供注册登录和邀请码加入；不做短信、邮箱验证、第三方登录和找回密码。
- 成员在外部完成付款，系统负责登记与确认。
- 首版不做成员退出或移除、结算后重新开账、退款、任务协作、票据上传、多币种和真实支付。
- 基础预算、分类汇总和 CSV 导出属于首版；动画、复杂图表和移动端精细适配不作为交付门槛。

### 完成标准

1. 从创建活动、多人记账到结清归档的流程可运行，刷新页面和重启服务后数据仍在。
2. 三种分摊方式金额守恒，结算确认具有权限校验和重复操作保护。
3. 角色丁在本机独立干净目录按 README 安装锁定依赖，统一完成整系统测试与复现，不要求四名成员分别验收。

5. 角色丁核对报告中的需求、界面、代码与测试映射；现场代码讲解归入课堂演示，不设四人独立验收门槛。

## 三 核心业务规则

### 金额与分摊

接口金额统一使用整数分，展示时才格式化为两位小数。前端把十进制输入按字符串转换为分，不依靠浮点乘法后取整；后端拒绝非整数分、非正总额和重复的分摊成员。

| 方式 | 计算规则 | 示例 |
| --- | --- | --- |
| 均摊 EQUAL | 总额除以人数取整数部分，余下的分按成员 ID 升序逐一分配 | 10000 分分给三人：3334、3333、3333 |
| 指定金额 EXACT | 各成员份额非负，合计必须严格等于总额 | 10000 分指定为 2000、3000、5000 |
| 按份数 SHARES | 份数为正整数；先取每份精确金额的整数部分，再按小数余数从大到小补足，余数相同按成员 ID 升序 | 60000 分按 2∶2∶1∶1：20000、20000、10000、10000 |

计算必须满足：每笔分摊合计等于费用总额；未参与该费用的成员承担零；相同输入总是产生相同输出。前端预览和保存使用同一个后端分摊服务，最终结果以后端为准。

### 余额与结算建议

对每位成员使用如下公式：

~~~text
余额 = 累计垫付 - 累计承担 + 已确认付出 - 已确认收到
正数表示应收，负数表示应付。
~~~

活动内全部余额之和必须为零。费用消费与结算付款分表保存，付款不进入活动消费总额。

建议算法把债务人和债权人分别按剩余额度降序、成员 ID 升序排序，每次匹配双方额度的较小值，直至可登记额度耗尽。首版保证金额正确和执行后余额归零，不声称获得全局最少转账次数。

待确认付款不改变正式余额，但会占用双方的可登记额度：

~~~text
可登记付出 = max(-当前余额, 0) - 待确认付出合计
可登记收到 = max( 当前余额, 0) - 待确认收到合计
~~~

转账建议使用这两个扣除占用后的额度，页面同时展示正式余额、待确认金额和可登记额度。付款金额必须为正，付款人与收款人不同，且不得超过双方可登记额度。

### 活动与付款状态

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE
    ACTIVE --> SETTLING: 创建者发起结算
    ACTIVE --> SETTLED: 封账时已经平账
    SETTLING --> SETTLED: 全部余额为零且没有待确认付款
    SETTLED --> ARCHIVED: 创建者归档
~~~

- ACTIVE：可加入成员、录入和修改费用；所有成员可查看本活动数据。邀请码由创建者查看并自行分享。
- SETTLING：冻结成员、费用、分摊和预算；允许登记、确认、拒绝或撤销付款。
- SETTLED：账务只读，等待创建者归档；发起结算时如已满足结清条件，直接完成该状态判定。
- ARCHIVED：只读查询与导出。

付款状态为 PENDING、CONFIRMED、REJECTED、CANCELLED。仅收款人可确认或拒绝，付款人可撤销自己的待确认付款；后三种状态均为终态。拒绝或撤销释放占用额度，确认以已确认流水影响余额。

### 权限与数据一致性

- 非活动成员不得读取或修改该活动的费用、成员、余额、统计和历史。
- 每个成员可录入费用，付款人可以是本活动的其他成员；仅费用记录者或活动创建者可编辑、删除该费用。
- 创建者不具有代替收款人确认的权限；所有状态校验由后端执行。
- 费用和分摊明细的变更、付款状态变更及其历史记录在同一数据库事务内完成。
- 删除费用采用逻辑删除，保留历史；编辑历史记录业务字段变更前后值，不记录密码或令牌。
- SQLite 写事务在读取余额和执行校验前取得写锁，统一使用短事务；封账与费用变更也经过同一事务规则，避免检查后状态改变。
- 费用创建可携带 UUID v4 格式的 request_id，以“活动、记录者用户、编号”唯一登记；相同请求重试返回已有费用的当前版本，内容不同或原费用已删除返回冲突，失败不占用编号。旧调用不带编号时保持每次创建的行为。此项为乙侧针对双击和网络重试补充的 FR04 验收规则。
- 付款登记携带客户端生成的 request_id，同一活动、付款人和 request_id 唯一。相同请求重试返回原记录；复用该 ID 但金额或收款人不同返回冲突。
- 重复确认已确认付款由同一收款人调用时返回既有结果，不能重复产生入账或历史；拒绝、撤销和确认竞争时只能有一个终态成功。

## 四 技术架构与数据设计

### 技术选择

| 层次 | 采用方案 | 用途 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus | 页面、表单、路由和登录状态 |
| 后端 | Python、FastAPI、Pydantic | REST API、输入校验、OpenAPI 文档 |

| 测试 | pytest、HTTPX、Vitest、Playwright | 业务计算、接口、前端交互和完整流程 |
| 协作 | GitHub Issues、功能分支、PR、GitHub Actions | 任务、审查、真实进度和持续集成 |

运行环境基线采用 Python 3.12 和 Node.js 22.12 以上的 22.x 版本；D1 锁定团队实际使用的依赖版本并提交锁文件。单机启动一个后端进程；SQLite 数据文件由后端独占管理，启用外键、WAL 和有限的锁等待，不放在网络共享目录中供多人直接打开。

认证实现使用成熟密码哈希库；JWT 密钥从环境变量读取。前端令牌仅保存在当前页面内存，刷新后重新登录，不在演示版本中实现持久登录。生产部署、跨公网 HTTPS 和运维不属于这一周的验收范围。

~~~mermaid
flowchart LR
    UI[Vue 页面与组件] --> API[FastAPI 路由和认证]
    API --> Service[活动与费用服务]
    API --> Ledger[余额与结算服务]
    Service --> Split[纯函数分摊模块]
    Service --> Store[SQLAlchemy 事务]
~~~

分摊与转账建议保持为独立纯函数；权限、活动状态、事务和历史记录在服务层处理。前端不承担最终账务判断。

### 数据实体

| 实体 | 主要内容 | 关键约束 |
| --- | --- | --- |
| User | 用户名、显示名、密码哈希 | 用户名唯一 |
| Activity | 名称、创建者、预算分、邀请码、状态 | 创建者也是成员，状态只允许合法流转 |

## 五 页面与接口约定

页面收敛为登录注册、活动列表和活动详情。活动详情默认费用明细，保留活动概览、成员、结算与付款、历史标签；顶部显示消费与预算，结算摘要常驻侧栏，封账和归档由活动进度条承载。创建和编辑费用共用表单。

API 前缀统一为 /api/v1，金额字段以 _cents 结尾，身份从服务端验证后的令牌取得。枚举使用前述英文值，展示使用中文。以下为 D1 接口契约基线，字段结构由对应负责人当天以 Pydantic 模型和 OpenAPI 固化，前端据此开发。

| 方法与路径 | 主要输入或输出 | 负责人 |
| --- | --- | --- |
| POST /auth/register、POST /auth/login、GET /auth/me | 注册信息、令牌、当前用户 | 乙 |
| GET、POST /activities | 用户活动列表、创建活动 | 乙 |
| GET、PATCH /activities/{id} | 活动详情；进行中更新名称和预算 | 乙 |
| POST /activities/join、GET /activities/{id}/members | 邀请码加入、成员列表 | 乙 |
| GET、POST /activities/{id}/expenses | 查询、创建费用 | 乙 |
| PATCH、DELETE /activities/{id}/expenses/{expense_id} | 更新费用与分摊、逻辑删除；携带 version | 乙 |
| POST /activities/{id}/split-preview | amount_cents、分摊方式、成员、金额或份数；返回分摊 | 丙 |
| GET /activities/{id}/balances、GET /activities/{id}/settlement-suggestions | 正式余额、待确认占用、可登记额度、建议 | 丙 |
| GET、POST /activities/{id}/payments | 付款列表；收款人、金额分和 request_id | 丙 |
| POST /activities/{id}/payments/{payment_id}/confirm、/reject、/cancel | 付款状态转换 | 丙 |
| POST /activities/{id}/start-settlement、POST /activities/{id}/archive | 封账、归档；结清由服务端自动判定 | 丙 |
| GET /activities/{id}/statistics、GET /activities/{id}/export.csv | 预算和消费汇总、费用明细 CSV | 丙 |
| GET /activities/{id}/audit-logs | 操作历史列表 | 乙 |

金额和状态输入错误使用 422，未认证使用 401，无权操作使用 403，资源不存在或不属于当前用户可访问活动使用 404，版本与业务状态冲突使用 409。前端保留未提交表单并显示后端错误，不把失败操作显示为成功。

乙侧接口在原 detail 之外提供稳定 code 与 retryable，便于甲区分过期版本、重复请求、封账和数据库暂忙。只有数据库暂忙标为可重试并返回 Retry-After；字段问题保留位置，未知异常使用通用响应。OpenAPI 显式声明错误模型，业务恢复规则见 [后端交接说明](BACKEND_HANDOFF.md)。

CSV 每笔有效费用一行，列出日期、分类、说明、付款人、总额、分摊方式及各成员份额。采用 UTF-8 BOM 编码；用户输入的文本按 CSV 规则转义，并处理以公式字符开头的文本，避免被表格软件当公式执行。

## 八 测试计划与预期结果

下表保留验收用例定义；实际结果及证据见 [系统验收报告](ACCEPTANCE_REPORT.md)。T01–T19 的业务标准保持不变；T20 按本次变更改为角色丁本机干净目录复现，结果见发布验收记录。课堂设备和现场演示单独记录，不冒充已执行。

| 用例 | 场景 | 预期结果 | 层次 |
| --- | --- | --- | --- |
| T01 | 100 元三人均摊 | 33.34、33.33、33.33，总额严格相等 | 单元 |
| T02 | 0.01 元按 1∶1∶1 分摊，改变输入排列 | 同一成员获得余数，结果始终可复现 | 单元 |
| T03 | 600 元按 2∶2∶1∶1 分摊 | 200、200、100、100 | 单元 |
| T04 | 指定金额合计错误、负份额、零份数、重复成员 | 拒绝保存，不留下费用或分摊残片 | 单元与接口 |
| T05 | 只有 A、B 分摊车费 | C 承担零，其他账单不受影响 | 单元与接口 |
| T06 | 三人出游示例 | A 应收 50，B 应付 10，C 应付 40 | 单元与接口 |
| T07 | C 登记支付 20，A 尚未确认 | 正式余额不变，双方可登记额度减少 20 | 接口 |
| T08 | A 确认 C 的 20 元付款 | A 应收 30，B 应付 10，C 应付 20 | 接口 |
| T09 | 同一登记请求重试、重复确认或并发确认 | 一条付款，只影响余额一次 | 接口与并发 |
| T10 | C 对 40 元债务并发登记两笔 30 元 | 最多一笔成功，不发生超额占用 | 接口与并发 |
| T11 | 同一付款被并发确认与撤销 | 只有一个终态成功，余额与状态一致 | 接口与并发 |
| T12 | 非收款人确认，或跨活动读取、修改记录 | 拒绝请求，数据不变 | 权限接口 |
| T13 | 封账后直接请求修改费用，或封账与编辑并发 | 不能出现封账成功后账目继续变化 | 接口与并发 |

| T15 | 事务在保存分摊或历史时失败 | 费用、分摊、付款与历史全部回滚至一致状态 | 接口 |
| T16 | 已结清时归档；未结清时归档 | 前者成功且只读，后者失败 | 接口与浏览器 |
| T17 | 没有费用或净额恰好全零时发起结算 | 正确判为已结清，不被卡在结算中 | 接口 |
| T18 | 预算、分类汇总、CSV 与付款并存 | 消费仍为费用总额，转账不被重复计入 | 接口与人工 |
| T19 | 服务重启、页面刷新、重新登录 | 已保存账务仍在，账号隔离有效 | 浏览器与人工 |
| T20 | 角色丁本机干净目录安装与三账号完整流程 | 按锁文件安装，完成记账至归档、CSV、重启和演示联合启动 | 角色丁统一验收 |

自动化测试使用独立临时数据库，不能复用演示数据库。并发测试使用独立连接访问同一个临时数据库文件，避免用进程内单连接测试冒充并发验证。浏览器测试为每个账号建立独立会话。

v1.0.0 发布门槛：角色丁按上述当前定义统一执行 T01–T20 并通过；前端类型检查和构建成功；无金额、权限、数据丢失或主流程阻塞问题。D6 以后发现此类缺陷优先修复并复测，图表美化让位于回归测试。
