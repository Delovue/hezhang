# 角色丙结算模块设计与算法说明

本文说明分摊、余额、结算建议、付款与活动生命周期的设计和算法，供实验报告“架构设计”“开发实现”两章引用，也是丙答辩的提纲。接口用法见[结算后端交接说明](SETTLEMENT_HANDOFF.md)，测试结果见[结算后端测试记录](SETTLEMENT_TEST_REPORT.md)。

## 一 分层结构

~~~mermaid
flowchart LR
    API[api/settlement、payments、reports<br/>路由与参数校验] --> Service[services/balance、payment、lifecycle、export<br/>读取数据、权限、事务、历史]
    Service --> Domain[domain/split、balance、settlement、payment、activity、statistics、export<br/>纯计算与业务规则]
    Service --> DB[(SQLite)]
~~~

| 层次 | 职责 | 不做的事 |
| --- | --- | --- |
| 领域层 domain | 金额计算、状态转换规则；输入数据，输出结果或抛出带错误码的领域错误 | 不访问数据库，不处理 HTTP 请求 |
| 服务层 services | 在写事务中读取费用、付款和成员，调用领域函数，写入结果和操作历史 | 不重复实现计算规则 |
| 路由层 api | 解析请求、认证、组装响应 | 不做业务判断 |

这样划分的原因：

1. 计算规则可以脱离数据库单独测试。丙的 127 项单元测试直接调用领域函数，运行一次不到 1 秒，可以覆盖大量边界和 200 组随机账本。
2. 分摊预览和保存费用必须得到相同结果。两者调用同一个 compute_split，乙的费用服务通过 calculate_split 接入，不存在两份实现。
3. 前端不承担最终账务判断，所有规则在后端执行。

## 二 金额表示

所有金额以整数“分”在接口、计算和数据库中流转，只在页面和 CSV 中格式化为元。

浮点数无法精确表示多数十进制小数：0.1 + 0.2 在二进制浮点下等于 0.30000000000000004。多笔累加后误差会让“分摊合计等于总额”“全部余额为零”这类判断失效。整数运算没有这个问题。

后端拒绝非整数、布尔值、非正总额（Pydantic 严格模式加领域层二次校验），金额上限 MAX_CENTS 为 JavaScript 安全整数 2⁵³−1，保证浏览器解析 JSON 时不丢精度。

只限制单笔金额还不够：两笔各自合法的费用累计后可能超过上限，余额和转账建议随之越界，建议无法直接登记，前端解析也会丢 1 分精度（PR #2 审查发现）。因此另加一条活动级约束：同一活动内有效费用总额不超过 MAX_CENTS，在费用创建和修改时于写锁内检查，修改时排除该笔费用的原金额，软删除费用不计入。由于垫付、承担、余额、可登记额度、已确认付款、统计和每条转账建议的绝对值都不超过费用总额，这一条约束就保证了所有金额字段都在安全范围内。格式化函数 format_cents 只用整数除法和取余，不经过浮点。

## 三 分摊算法

三种方式都满足三条性质：各成员份额之和严格等于总额；未参与者承担零；相同输入（与成员顺序无关）总是得到相同输出。结果一律按成员 ID 升序返回。

### 均摊 EQUAL

设总额 T 分、n 人，`q, r = divmod(T, n)`。按成员 ID 升序，前 r 人得 q+1 分，其余得 q 分。

合计 = r(q+1) + (n−r)q = nq + r = T。由于只依赖成员 ID 顺序，输入顺序变化不影响结果。

例：10000 分三人 → q=3333、r=1 → 3334、3333、3333。

### 指定金额 EXACT

每人份额是非负整数分，合计必须严格等于 T，否则拒绝并在提示中给出实际合计。不做任何自动调整，避免“系统替用户改了金额”。

### 按份数 SHARES

设成员 i 的份数为 wᵢ，总份数 W。精确份额 T·wᵢ/W 通常不是整数，采用最大余数法：

1. 用整数除法 `aᵢ, rᵢ = divmod(T·wᵢ, W)`，aᵢ 为整数部分，rᵢ 为余数（等价于小数部分乘 W，全程不用浮点）。
2. 剩余未分配 L = T − Σaᵢ 分，可证 0 ≤ L < n。
3. 按余数 rᵢ 从大到小、余数相同按成员 ID 升序排序，前 L 人各补 1 分。

例：5 分按 1∶2∶4 分给成员 1、2、3。精确值 0.71、1.43、2.86；整数部分 0、1、2，合计 3，剩 2 分；余数分别为 5、3、6（÷7），成员 3、1 余数最大，各补 1 分，结果为 1、1、3。

均摊可以看作每人 1 份的按份数分摊，此时余数全部相同，按 ID 升序补足，与均摊规则一致。

## 四 余额与可登记额度

对每位成员：

~~~text
余额 = 累计垫付 − 累计承担 + 已确认付出 − 已确认收到
正数表示应收，负数表示应付。
~~~

**零和性质。** 每笔费用使付款人的垫付增加 T，各成员的承担合计也增加 T，对全体余额之和贡献为零；每笔已确认付款使付款人 +x、收款人 −x，贡献也为零。因此活动内全部余额之和恒为零。这一性质在随机账本测试中逐组验证。

余额不落库，每次请求由有效费用（排除软删除）、分摊和已确认付款重新计算。这样不会出现“余额表与流水不一致”，代价是每次计算要读全部流水；课程场景下一个活动只有几十笔记录，开销可以忽略。

**可登记额度。** 待确认付款不改变余额，但会占用额度：

~~~text
可登记付出 = max(−余额, 0) − 待确认付出合计
可登记收到 = max( 余额, 0) − 待确认收到合计
~~~

如果不扣除待确认金额，C 欠 40 元时可以先登记 30 元、在对方确认前再登记 30 元，两笔都确认后 C 反而多付 20 元。扣除占用后，第二笔只能登记 10 元以内。拒绝或撤销付款会释放占用。

## 五 转账建议

建议基于可登记额度，即已经扣除待确认的部分：

1. 取可登记付出大于 0 的成员为债务人，可登记收到大于 0 的成员为债权人。
2. 每轮选剩余额度最大的债务人和最大的债权人（额度相同按成员 ID 升序），转账金额取二者较小值。
3. 额度降为 0 的一方移出，重复直到任一方为空。

**正确性。** 由零和性质，债务人额度之和等于债权人额度之和，所以两边同时耗尽，执行全部建议后余额全部归零。每轮至少让一方归零，n 个有额度的成员最多产生 n−1 笔转账。

**不保证次数最少。** 求最少转账次数需要把成员划分成尽可能多的“和为零”的小组，属于 NP 困难问题。开发计划明确首版不追求全局最优。用程序在小规模账本中搜索到的反例：

| 成员 | A | B | C | D | E |
| --- | --- | --- | --- | --- | --- |
| 余额 | 应收 30 | 应收 20 | 应收 20 | 应付 30 | 应付 40 |

贪心结果为 E→A 30、D→B 20、D→C 10、E→C 10，共 4 笔；最优为 D→A 30、E→B 20、E→C 20，共 3 笔。

生成建议只是计算，不写入任何数据；成员可以不按建议付款，只要不超过可登记额度。

## 六 付款状态机

~~~mermaid
stateDiagram-v2
    [*] --> PENDING: 付款人登记
    PENDING --> CONFIRMED: 收款人确认
    PENDING --> REJECTED: 收款人拒绝
    PENDING --> CANCELLED: 付款人撤销
~~~

| 规则 | 实现 |
| --- | --- |
| 只有收款人能确认或拒绝，只有付款人能撤销；创建者也不能代确认 | 领域函数先检查操作者，否则 403 PAYMENT_ACTION_FORBIDDEN |
| 三个终态不可再变 | 非 PENDING 且不是同一动作时返回 409 PAYMENT_STATUS_CONFLICT |
| 重复执行同一动作返回原结果 | 返回 changed=False，服务层不写付款、不写历史，因此不会重复入账 |
| 只有结算中的活动能登记或处理付款 | 否则 409 PAYMENTS_CLOSED；重复确认的判断先于此检查，活动自动结清后再重试也返回原结果 |

付款登记要求客户端生成 request_id（UUID v4）。同一活动、同一付款人、同一编号由数据库唯一约束保护：内容相同的重试返回原记录（200），内容不同返回 409 REQUEST_ID_CONFLICT。

## 七 活动生命周期

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE
    ACTIVE --> SETTLING: 创建者发起结算
    ACTIVE --> SETTLED: 发起时已结清
    SETTLING --> SETTLED: 最后一笔确认后自动判定
    SETTLED --> ARCHIVED: 创建者归档
~~~

结清条件是全部余额为零且没有待确认付款。没有费用或净额恰好为零时，发起结算直接进入 SETTLED，不会卡在结算中。每次付款状态变化后服务层重新计算余额，满足条件即在同一事务内把活动改为 SETTLED 并写入 ACTIVITY_SETTLED 历史，不需要人工操作。

进入 SETTLING 后，乙的费用、成员、预算写接口统一返回 409 ACTIVITY_LOCKED，账目冻结。

## 八 并发与事务

SQLite 同一时间只允许一个写事务。乙的 transaction(write=True) 在事务开始时执行 BEGIN IMMEDIATE，先取得写锁，再读取状态和余额。丙的所有写操作（登记、确认、拒绝、撤销、封账、归档）都在这样的事务中完成：

~~~text
取得写锁 → 读取活动状态、付款状态、最新余额与待确认占用 → 领域函数校验 → 写入 → 写历史 → 提交
~~~

| 场景 | 如果先读后加锁会怎样 | 加锁后的结果 |
| --- | --- | --- |
| T10：C 欠 40 元，同时登记两笔 30 元 | 两个请求都读到额度 40，都通过校验，超额 20 元 | 后到的请求等待写锁，拿到锁后读到已占用 30，只剩 10，返回 409 |
| T11：确认与撤销同时到达 | 两者都读到 PENDING，各自写入不同终态 | 后到者读到已变更的终态，返回 409 |
| T09：同时重复确认 | 两次都写入 CONFIRMED 和历史 | 后到者读到 CONFIRMED，返回原结果，不写历史 |
| T13：封账与改账同时到达 | 改账读到 ACTIVE 后，封账先提交，改账仍然写入 | 二者串行；封账之后的改账读到 SETTLING，返回 409 |

付款、活动状态和历史在同一事务中提交，任何一步失败全部回滚。测试中在最后一笔确认写结清历史时注入异常，验证付款仍为 PENDING、活动仍为 SETTLING、历史没有新增。

## 九 统计与导出

统计只读取有效费用，不读取付款，因此成员间的结算不会被算成消费。未设预算时不判断超预算，预算为 0 是有效值；超预算时剩余预算为负数。

CSV 每笔费用一行，成员各占一列，金额与页面一致。编码为带 BOM 的 UTF-8，Excel 直接打开中文不乱码。以 = + − @ 或制表、回车开头的用户文本前置单引号，防止 CSV 注入：例如费用说明写成 `=HYPERLINK(...)` 时，表格软件会把它当公式执行。显示名重复时列名附加成员编号。

## 十 已知局限

- 转账建议不保证次数最少，见第五节。
- 单个活动的有效费用总额上限为 MAX_CENTS，约 90 万亿元，对课程场景没有实际影响，见第二节。
- 余额每次重新计算，活动数据量很大时需要改为增量维护或缓存，首版不需要。
- 只支持人民币和单一付款人；不支持退款、结算后重新开账和成员退出，这些在开发计划中已排除。
- SQLite 写锁使所有写请求串行，适合本地演示和小组规模，不适合高并发部署。
